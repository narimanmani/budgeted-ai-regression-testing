# Separate development and fresh validation (v8)

This is a new prospective study version. The closed v7 Dify failure and all its
costs remain part of the record. The CG1 selector remains byte-identical. The new
development workload addresses native record lookup and literal copying before
fresh validation, without running CG1 or ranking its effectiveness.

Root must freeze the generator, separate cohort seeds, both task/source/contract
frames, P0/P1 instructions, source interventions, runtime configuration and this
protocol before the first development answer. Run both fixed candidates fully.
Choose the first eligible candidate in the fixed P0/P1 order. Eligibility requires
all16 healthy answers correct, two repeated fault-witness failures and the eight
designated bad-state control passes. If neither candidate qualifies, stop.

After selection, freeze the selected configuration and complete fresh validation
frame before acquiring any validation answer. Fresh qualification uses32 queries
per app; a separate48-query reference bank follows only a passed gate. Both apps
must finish these acquisitions and the whole-design resource projection before
any policy comparison or warm-history acquisition.

The scientific plan has2624 native units:192 development,64 fresh qualification,
96 reference,192 paid old-state features,640 own warm-history acquisitions and
1440 selected comparisons. With2071 prior units and3 planned provider probes,
302 units remain under the unchanged5000-unit cap. Startup, setup, probe, failed
and incomplete work remains counted. This projection is a ceiling for the fixed
design, not permission to spend untracked retries.

The new eight-task main runner preserves K=2/4, five arms, cold/warm histories,
two repetitions and80 trajectories. Use common paid state preparation outside
each policy's episode timer so a method does not inherit a lazy API-start charge.
Each standalone operational cost view still includes its required setup and
shared feature acquisition. Physical shared work is counted once.

These are fresh workload instances in the same two applications and historical
fault families. Application-specific development has occurred. The appropriate
claim is held-out-workload transfer, with full enrollment attrition disclosed.
Dense ingestion dependencies may leave selective impact evidence untested; the
fixed factual checker also leaves judgment-mechanism interactions untested.
Neither a passing gate nor working software establishes CG1 effectiveness.

`gates.py` provides pure exact-frame checks and fixed development selection. Its
saved-data gate rechecks native/wrapper/root-reservation identity, explicit
cohort/configuration hashes and both unchanged factual checker implementations.
It never starts an application or model. Raw source/configuration and actual
context adequacy audits remain separate prerequisites.
